# Crime Hotspot Analysis (geospatial analytics project)

Cleans crime-report data with coordinates, finds spatial hotspots with DBSCAN, maps them (interactive
heatmaps + static figures), analyses time trends, relates crime to neighbourhood socioeconomics, and
turns the results into a transparent patrol-allocation proposal.

> **Read this first: the bundled results use SYNTHETIC data.** The sandbox this was built in had no
> internet, so the pipeline was run on a fabricated Chicago-like dataset with the same columns as the real
> portal data (including deliberate data-quality errors for the cleaning step). The code is the deliverable;
> the findings in `REPORT.md` describe the simulation, not a real city. Run with `--source chicago` for real results.

## Quick start

```bash
pip install -r requirements.txt
python run_analysis.py                      # synthetic demo, ~20 s, works offline
python run_analysis.py --source chicago     # real City of Chicago open data (needs internet)
```

Then open `REPORT.md`, `outputs/maps/hotspot_map.html` (toggle layers top-right; click hotspots for details),
and the PNGs in `outputs/figures/`.

## Project layout

```
run_analysis.py        command-line entry point (runs all 8 steps)
crimegeo/
  data_sources.py      synthetic generator; Chicago open-data (Socrata) loader; CSV loader
  cleaning.py          dedupe, date parsing, coordinate repair, audit trail
  clustering.py        projection, DBSCAN on a weighted grid, hotspot summaries, sensitivity grid
  temporal.py          monthly decomposition (numpy), YoY, seasonal index, hour x weekday
  socioeconomic.py     zone rates, Spearman, VIF screening, OLS, Moran's I (numpy/scipy only)
  allocation.py        risk-weighted patrol allocation (all assumptions are parameters)
  mapping.py           Leaflet HTML map builder + optional Folium builder
  plots.py             static figures
  report.py            builds REPORT.md from the computed results
data/                  raw inputs saved by each run
outputs/               figures, maps, tables
```

## Using real data

**Chicago open data (`--source chicago`).** Downloads crimes (dataset `ijzp-q8t2`) and community-area
socioeconomic indicators (`kn9c-c2s2`) from data.cityofchicago.org. **This path has not been run**: the build
sandbox could not reach the internet. On first run, check that the socioeconomic column names were mapped
(see `_SOCIO_RENAMES` in `data_sources.py`) and that `outputs/tables/data_cleaning_audit.csv` looks sensible.
Two things to know:

* The socioeconomic dataset has **no population column**. Without one the analysis falls back to raw counts per
  zone (confounded by zone size). Supply `--population-csv pop.csv` (columns `zone_id,population`, e.g. from the
  Census/ACS) to get per-1,000-resident rates.
* Those indicators are from 2008-2012. Newer community-area data would be a better match for recent crime.

Options: `--start 2023-01-01 --end 2025-12-31 --app-token <Socrata token>` (a token raises rate limits).

**Your own CSV (`--source csv --csv crimes.csv --demographics-csv zones.csv`).**

* Crimes: `case_number, date, primary_type, latitude, longitude, community_area`
  (`date` may be ISO-8601 or `MM/DD/YYYY hh:mm:ss AM`).
* Zones: `zone_id, zone_name, population, poverty_pct, unemployment_pct, no_hs_diploma_pct,
  crowded_housing_pct, dependency_pct, per_capita_income` (optionally `hardship_index`).
  `zone_id` must match `community_area`.

For a different city, update `BBOX`, `CITY`, `SEVERITY` weights and (if needed) the crime-type groups in `crimegeo/config.py`.

## Key parameters

| Flag | Default | Meaning |
|---|---|---|
| `--eps` | 250 | DBSCAN radius in metres (about one to two city blocks) |
| `--density-multiple` | 10 | `min_samples` = this x the incidents an eps-disc holds at average density |
| `--patrol-hours` | 1000 | illustrative weekly deployable hours |
| `--directed-share` | 0.70 | share of hours that is hotspot-directed (rest is baseline zone patrol) |
| `--alpha` | 0.75 | directed hours proportional to risk^alpha (alpha < 1 spreads resources more evenly) |

The allocation parameters are assumptions to tune with operational input, not findings.

## Method notes

* **DBSCAN on a weighted 25 m grid.** Incidents are snapped to 25 m cells and clustered with `sample_weight`
  = incidents per cell. This is equivalent to DBSCAN on the raw points but avoids memory blow-up when thousands
  of incidents sit on a few street corners.
* **Hotspots are ranked by severity-weighted risk**, not raw count. The weights in `config.py` are illustrative.
* **Maps** use Leaflet + leaflet.heat loaded from a CDN, so the HTML needs an internet connection to show
  basemap tiles and heat layers. Heat layers are aggregated to a 150 m grid, keeping the file around 2 MB.
* **What was and wasn't verified here:** the full pipeline ran end to end on synthetic data and the static
  figures were inspected. The interactive HTML was checked for valid JavaScript and well-formed embedded data,
  but **not rendered in a browser**. The Folium builder was only syntax-checked.

## Limitations (details in REPORT.md, section 7)

Reported crime is not all crime; hotspot patrol can create feedback loops in recorded counts; zone-level
correlations describe places, not people; DBSCAN output depends on its parameters (see the sensitivity table).
Treat outputs as decision support to be reviewed and evaluated, not as automatic deployment orders.
